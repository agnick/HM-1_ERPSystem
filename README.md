# ERP System for Moscow Zoo

## Обзор проекта

Данное консольное приложение представляет собой ERP-систему для Московского зоопарка. Система позволяет:
- Принимать животных на баланс зоопарка с предварительной проверкой их здоровья ветеринарной клиникой.
- Вести учёт потребляемой еды (в кг) каждым животным в сутки.
- Формировать отчёты по количеству животных, общей норме потребления еды, а также список животных для контактного зоопарка (животные с уровнем доброты > 5).
- Учёт инвентаризационных вещей (например, столы, компьютеры) вместе с животными, имеющими уникальные номера и наименования.

## Применённые принципы SOLID

### Single Responsibility Principle (SRP)
- **Классы с единственной ответственностью:**  
  - `Animal` и его наследники (`Herbo`, `Monkey`, `Predator`, `Tiger`, `Wolf` и др.) отвечают только за управление характеристиками животных.
  - `Thing` и его наследники (`Table`, `Computer`) отвечают за управление инвентарными вещами.
  - `Zoo` занимается координацией приёма животных и вещей, а также формированием отчётов.
  - `VetClinic` реализует логику проверки состояния здоровья животных.
  
Каждый класс имеет единую зону ответственности, что упрощает поддержку и расширение системы.

### Open/Closed Principle (OCP)
- **Расширяемость без изменения существующего кода:**  
  - Базовый класс `Animal` можно расширять, создавая новые типы животных (например, `Herbo`, `Predator`, `Monkey` и т.д.), не изменяя его внутреннюю реализацию.
  - Для новых типов инвентарных объектов достаточно создать новые классы, наследуясь от `Thing`.
  
Таким образом, система открыта для расширения, но закрыта для модификаций базового функционала.

### Liskov Substitution Principle (LSP)
- **Замещаемость наследников базовым классом:**  
  - Любой объект-наследник класса `Animal` (например, `Tiger`, `Wolf`, `Herbo`) может быть использован там, где требуется объект типа `Animal`.  
  - Это гарантирует, что при использовании базового типа не возникнут ошибки, если объект окажется экземпляром производного класса.

### Interface Segregation Principle (ISP)
- **Разбиение больших интерфейсов на более специализированные:**  
  - Интерфейсы `IAlive`, `IInventory` и `INameable` разделяют обязанности между собой:
    - `IAlive` предоставляет свойство `Food` для учёта потребляемой еды.
    - `IInventory` отвечает за уникальный инвентаризационный номер.
    - `INameable` предоставляет наименование объекта.
  - Это позволяет классам реализовывать только те методы и свойства, которые им действительно нужны.

### Dependency Inversion Principle (DIP)
- **Зависимость от абстракций, а не от конкретных реализаций:**  
  - Класс `Zoo` зависит от интерфейса `IVetClinic`, а не от конкретной реализации `VetClinic`. Это позволяет легко подменять реализацию проверки здоровья, если потребуется.
  - DI-контейнер используется для регистрации и инъекции зависимостей, что повышает модульность и тестируемость приложения.

## Dependency Injection (DI)

В проекте используется DI-контейнер для централизованного управления зависимостями. Это обеспечивает:
- **Слабую связанность компонентов:** Зависимости разрешаются через интерфейсы.
- **Упрощённое тестирование:** Возможность замены реальных реализаций мок-объектами при тестировании.
- **Удобство конфигурации:** Все зависимости регистрируются в одном месте, что облегчает дальнейшее расширение и модификацию системы.

## Инструкция по запуску

### Шаги для запуска
1. **Клонируйте репозиторий:**
    ```bash
    git clone <URL вашего репозитория>
    cd <имя каталога проекта>
    ```

2. **Соберите проект:**
    ```bash
    dotnet build
    ```

3. **Запустите приложение:**
    ```bash
    dotnet run
    ```
